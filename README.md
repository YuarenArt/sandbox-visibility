# sandbox-visibility

Стенд для измерения того, что именно видно с хоста о действиях нагрузки внутри
песочницы, и кому эти действия приписаны.

Восемь конфигураций: без песочницы, три конфигурации gVisor, две виртуальные
машины на qemu с разным способом отдать гостю файловую систему, Firecracker и
пустой прогон как отрицательный контроль. Одинаковый набор из десяти действий в
каждой, наблюдатель на точках трассировки системных вызовов.

Результаты и выводы: [RESULTS.md](RESULTS.md). Что именно измеряется и почему
именно так: [DESIGN.md](DESIGN.md).

## Главное про метод

Ноль в такой таблице означает две разные вещи: граница не пропустила операцию,
либо наблюдатель в этот момент не работал. Различать их обязательно, иначе
измеряется качество обвязки, а не предмет. Поэтому у каждой строки есть
собственные доказательства.

- **Самопроверка проб.** `probecheck` делает девять системных вызовов напрямую
  через `syscall()`, каждый со своим маркером. Если хоть одна проба молчит,
  прогон не запускается. Ловит случаи вида «проба висит на `unlinkat`, а libc
  зовёт `unlink`».
- **Хостовая проба.** Заведомая операция с маркером на самом хосте внутри окна
  наблюдения. Нет её в трейсе, значит наблюдатель недоказуем, строка негодна.
- **Маркер в имени образа.** Образ диска и ядро гостя называются
  идентификатором прогона, их открывает сам монитор виртуальной машины. Даёт
  доказательство живости строкам, где ожидается ноль.
- **Отрицательный контроль.** Та же песочница, тот же идентификатор, ноль
  действий.
- **Знаменатель от нагрузки.** Полнота считается по операциям, которые гость
  выполнил успешно; исход каждой пишется с `errno`.
- **Учёт потерь и нефильтрованные гистограммы.** Ноль маркеров при десятках
  тысяч событий у монитора означает границу, ноль и там и там означает
  сломанную обвязку.

## Запуск

Нужны root, `/dev/kvm`, `gcc`, `mke2fs`, `debugfs`, `nc`.

```
sudo ./run-all.sh 3
```

Пересобирает бинари, прогоняет самопроверку проб, обе руки и сводку. Аргумент
это число повторов на среду.

Отдельно:

```
sudo ./run/selftest.sh              # только проверка проб
sudo ./run/host-and-gvisor.sh       # хост и gVisor
sudo ./run/vms.sh                   # виртуальные машины
./analyze.sh                        # сводка по results/
```

## Что нужно доложить самому

В `bin/` ожидаются сторонние бинари, в репозиторий они не входят:

- `bpftrace` версии 0.26 или новее. Релизный сборка это AppImage поверх
  nix-бандла, её надо распаковать (`--appimage-extract`) в `bin/squashfs-root`,
  прямой запуск монтирует себе tmpfs и оставляет монтирования после себя.
- `runsc` из релизов gVisor.
- `firecracker` из релизов проекта.
- Гостевое ядро, `qemu` и `virtiofsd`. Берутся из сборки `kata-static`, путь
  прописан в `run/vms.sh`.

## Чего стенд не делает

Перечислено, чтобы это не всплыло как открытие.

Каналов наблюдения реализовано два из шести: точки трассировки системных
вызовов и жизненный цикл процессов. Обхода `/proc`, `inotify`, чтения байтов
образа как измеряемого канала и собственного экспорта рантайма нет. Строки
`runc` нет, gVisor везде с `--network=host`. Задержка обнаружения пишется с
обеих сторон, но часы гостя и хоста в разных базах, и сведение не реализовано.
`read` не инструментирован: аргумент вызова это дескриптор, а не путь.
Настоящие средства защиты не запускались, меряется собственный наблюдатель на
тех же точках. Kata меряется не как продукт: берутся её гостевое ядро, `qemu` и
`virtiofsd`, но без containerd, `kata-runtime` и агента внутри гостя.
